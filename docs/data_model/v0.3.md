## Why this document exists, and what it is not

Day 26 found one instance of this: a sparsity claim cited as "Data model
v0.3 §3" that does not exist anywhere in the repo. Day 27 Objective 3
asked how widespread that pattern is. It is the whole numbering scheme —
every section this codebase has ever cited as part of "the data model"
was conversational or assumed architecture, never checked in.

**This document is a reconstruction, not a rediscovery.** Sections below
that correspond to real, implemented, tested code are numbered to match
their existing citations (§0, §10, §15, §17) and describe what the code
*actually does* — verified against the implementation, not recalled from
memory of what a prior conversation might have intended. Where a cited
provision has NO implementation and NO prior record of its intended
content (constraint typing, the hypothesis store), this document does
**not** invent one. It says so, explicitly, in its own section below —
manufacturing plausible-sounding content for an unwritten spec would
repeat the exact failure this document exists to close, one level down.

Six other provisions this project has built and cited as settled
architecture are NOT renumbered into this document — they already have a
real, versioned home in `docs/adr/`, and duplicating them here under a
new number would create two sources of truth for the same decision. They
are indexed in the catalog below, cross-referenced to their ADR.

## §0 — Twin-revision consistency

**Status: IMPLEMENTED.** `src/model/world.py`. A world-frame position
storable without its `twin_rev` means re-versioning the site's 3D twin
(camera recalibration, remount, a redrawn zone) silently changes what a
stored position means, with no record of the drift — "precisely the
failure §0 of the data model exists to prevent" (the module's own
existing docstring language, verified verbatim at
`src/model/world.py:9`, quoted here as evidence this section's INTENT
was always real even though its DEFINITION was never written down).

- `WorldPosition` requires `twin_rev` as an undefaulted field (same
  pattern as `Relationship`'s bitemporal fields — see §5-equivalent
  content in ADR 0005 below).
- `WorldPosition.distance_to` / `.reproject` raise `TwinRevError` when
  two revisions differ and no `TwinRevTransform` is supplied — no
  `__sub__`/`__add__` exists at all, so silent cross-revision arithmetic
  was never representable.
- `TwinRevTransformRegistry.resolve` raises for an unregistered
  revision pair rather than defaulting to identity.

Tested: `tests/test_model_world.py` (Day-13 falsification test 3 is the
regression guard this closes — see that test file's own module
docstring for the traced bug).

## §10 — Confidence calibration

**Status: IMPLEMENTED.** `src/model/evidence.py`. A confidence score
must not claim to be a probability without a `CalibrationRecord` behind
it — "reports 92% confidence, right 70% of the time" is the failure mode
named directly in `src/estimator/consistency.py:21`, extended from a
discrete classification context (where this section's citations
originate) to continuous state (NIS/NEES, `src/estimator/state.py:11`).

- `Confidence = UncalibratedScore | CalibratedProbability` — a union,
  not a bare float. `UncalibratedScore` has no `probability` attribute
  at all (a caller cannot accidentally treat it as one).
- `CalibratedProbability` requires a `CalibrationRecord` as a
  non-optional constructor argument.
- The estimator's own consistency stage (§15 below) is this section's
  rule "extended to continuous state": `StateEstimate.residuals` cannot
  be empty and must contain an `nis`-kind entry, the continuous
  analogue of refusing an uncalibrated score.

Tested: `tests/test_model_evidence.py`. Documented informally in Day
13's own report table (`FOUNDATION_REPORT.md`, the `Confidence cannot
claim to be a probability without calibration` row) — real, tested,
never previously given a standalone numbered document until this one.

## §15 — The estimator contract

**Status: IMPLEMENTED, four stages RECONSTRUCTED here for the first
time.** Cited 20+ times across `src/estimator/` (`filter.py`,
`motion_model.py`, `measurement_model.py`, `imm.py`, `joint.py`,
`state.py`, `consistency.py`) as "the estimator contract," but **only
stage 4 was ever named anywhere** ("stage 4 of §15 always runs" —
`src/estimator/state.py:13`, `src/estimator/consistency.py:1`, and
three more sites). Stages 1-3 were never enumerated in any prior
document; the closest prior description is `filter.py`'s own three-word
informal summary, "predict -> observe -> correct." The four stages
below are reconstructed directly from the actual, tested code structure
— not recalled from a prior definition, because none existed to recall.

1. **Motion model** (predict). `src/estimator/motion_model.py` —
   `MotionModel.F`/`.Q`: how a state propagates over `dt` and how much
   process noise enters while it does. Swappable per entity kind,
   versioned by `.sha`.
2. **Measurement model** (observe). `src/estimator/measurement_model.py`
   — `MeasurementModel.H`/`.R`: what a sensor predicts, and how much to
   trust one reading. Never sees a prior (§17).
3. **Update** (correct). `src/estimator/filter.py`'s Joseph-form Kalman
   update (`run_single_entity_filter`) and its joint generalization
   (`src/estimator/joint.py`'s `run_joint_filter`) — combines predicted
   state with a new observation via the swappable §15.1/§15.2
   components.
4. **Consistency** (always runs). `src/estimator/consistency.py` — NIS
   live on every update, NEES at evaluation time against GT; a
   `StateEstimate` cannot be constructed without at least one `nis`-kind
   residual (computed or an explicit stub naming why not) — the §10
   calibration rule's continuous-state form.

Two structural rules also cited under §15, both implemented and tested:
`StateEstimate.require_comparable`'s three-way `sha` key
(`motion_model_sha`/`measurement_model_sha`/`update_rule_sha` — two
estimates are comparable only if all three agree), and
`motion_model_sha` naming which stage-1 component produced a given
factor.

## §17 — The prior firewall

**Status: IMPLEMENTED.** No function in the estimator's public API
accepts a parameter that could carry a behavioral prior — a belief about
where an entity "probably" is or how it "probably" moves, injected from
outside the observation stream itself. Enforced and tested directly via
`inspect.signature`, not merely documented as a convention:

- `run_single_entity_filter` (`tests/test_estimator_filter.py`,
  `test_run_single_entity_filter_has_no_prior_parameter`)
- `resolve_state` (same file,
  `test_resolve_state_has_no_prior_parameter`)
- IMM's mode mixing (`tests/test_estimator_imm.py`, "§17 -- the prior
  firewall, a new code path, tested again")
- `run_joint_filter` / `resolve_joint_state`
  (`tests/test_estimator_joint.py`, re-tested Day 26 against the new
  multi-entity code path specifically, per that module's own docstring)

The first state in any graph bootstraps from the first observation
alone (position = that observation, velocity = 0, covariance = a
declared-large prior on velocity only, never a claim about *where* the
entity is). Every new code path this project has added to the estimator
since Day 20 has re-tested this rule independently rather than assuming
it inherited from the code it extends — the closest thing to an
enforcement mechanism this repository has for a rule with no
checked-in definition until today.

## Provisions cited as settled, with NO implementation and NO prior record

### Constraint typing — hard vs. twin-dependent

Cited as an audit target with the specific claim that constraint
violations should raise "twin-revision hypotheses." Grep-verified across
`src/`, `tests/`, `docs/adr/`, and `FOUNDATION_REPORT.md`: the ONLY
trace of this anywhere is a single stub label,
`_CONSTRAINT_CONSUMER = "twin-revision hypothesis (not yet
implemented)"` (`src/estimator/consistency.py:82`), routed via
`ConsistencyResidual(kind="constraint", ...)` and never populated with a
real value. There is no `ConstraintKind` type, no enumeration of "hard"
vs. "twin-dependent," and no code path that raises anything resembling
a "twin-revision hypothesis" object. **Classification: ASSUMED,
NOWHERE RECORDED.**

### The hypothesis store and its typed death causes, including `PRUNED_BY_BUDGET`

Grep-verified: `PRUNED_BY_BUDGET`, `HypothesisStore`, `DeathCause`, and
`death_cause` appear ZERO times anywhere in this repository, including
in every prior day's `FOUNDATION_REPORT.md` entry and every ADR.
"Hypothesis management" itself IS a real, long-standing punch-list item
(carried on nearly every day's ordered list since Day 5, "furthest out")
— but at no point, across 27 days, has it ever been specified with the
precision `PRUNED_BY_BUDGET` implies (a literal, named death-cause
enumeration value). This is the sharpest instance this audit found: a
specific implementation detail cited as if established, with literally
no antecedent anywhere in version control. **Classification: ASSUMED,
NOWHERE RECORDED** — more starkly than any other provision audited
today, because even the *general* topic's citations never reached this
level of specificity before being asked about directly.
